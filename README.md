# Mechamusume（机娘）
- 摘要：A deterministic architecture solution for deep expansion of intelligent AI in dialogue and behavior, enabling the practical deployment of artificial companions with specific autonomous personalities.（一套让智能AI在对话/行为上进行深度拓展的确定性架构方案，让具有特定自主人格的人工伴侣能够落地应用。）/（対話と行動において知能AIの深い拡張を可能にする決定論的アーキテクチャ方案であり、特定の自律的人格を持つ人工伴侶の実用的な展開を可能にする。）
- 关键词：Composite Routing State Mapper - Preset AI Response System；Causal Logic；Quantum Leap (Universal State Mapping)；
- 目前游戏NPC拟人方面存在的问题：Generative AI (LLMs) have, to a certain extent, enhanced the novelty and positive feedback that traditional linear-narrative NPC interaction lacks. However, the probabilistic model's contextual hallucination, the continuous payment model, and memory-rule plugins cannot provide players with long-term, stable, deep-companionship positive feedback. The jailbreak risk and the charging mechanism of probabilistic models are in practice unsuitable for vendors' compliant operations.To make NPC AI more vivid while maintaining operational compliance, I designed this deterministic composite preset architecture.（生成AI“LLM”一定程度上提升了传统线性叙事的NPC互动所不具有的新鲜感正反馈，但概率模型的上下文幻觉问题、持续付费模式、记忆规则插件等无法给玩家带来长期稳定的深度陪伴正反馈。概率模型的穿甲风险与收费机制实际并不适合厂商合规运营。为了在运营合规上让NPC的AI更加生动，我设计了这套确定性复合预设方案。）

## 架构方案、实现逻辑及映射表结构
### 复合路由状态映射逻辑定义
- 前提：影响角色状态的多个变量范围定义、变动规则独立模块在其他目录，不参与主模块和角色状态模块的耦合
- （低耦合）方案1主模块当前复合路由状态ID=角色状态模块的最终路由ID（角色状态模块负责生成最终路由ID，主模块直接用自己的空状态ID去匹配对方的ID）；
- （中耦合）方案2可交互角色状态以及角色变量是单独模块，随着场景和时间和随机数进行变化状态。然后主模块就是用多个主角无实值变量去匹配可交互角色状态的角色变量，然后根据多个已有实值的主角变量return复合路由状态的ID（就是反过来，主模块用空变量匹配对方的变量，自己生成最终路由ID）
- （高耦合）方案3复合路由状态ID映射和角色变量状态变化都放在主模块
- （完全隔离）方案4角色状态一个模块，ID生成计算一个模块，读取ID一个主模块（多任务完全隔离）
- （完全耦合）方案5把状态变量定义变化规则多个独立模块和ID生成模块和人物状态模块等等全部塞进主模块
- 声明1：多→单→多→单的嵌套结构 或 多→最终状态ID→单多个中转ID模块→主模块ID读取的冗余结构 也是这几种耦合而已
- 声明2：多个输入关键词→唯一意图识别的映射结构，也是复合路由状态映射（任何前端输入到中端处理到后端输出都适用：通用量子跃迁技术CRSM-PARS）

### 多种路由方案对比
- （超级方案）方案1-5复合路由状态映射路线：如方案2，预设输入→当前变量A=当前角色状态其一→当前变量B=当前角色状态其一→……→当前变量E=当前角色状态其一→复合路由状态ID=当前变量A+B+C+D+E→资源库ID=复合路由状态ID→输出复合资源
- （超级混合方案）复合路由状态映射+跳转守卫路线：前面用映射表管理复合路由状态映射具体分支，后面用menu和if管理具体分支内容输出到循环结束
- （高级替代方案）简单路由+逐条守卫路线：通过意图识别/预设menu跳转功能进行单次路由到细致拆分的特定守卫条件模块往下跑，用守卫条件成立输出，不用ID映射输出
- （中级替代方案）逐条守卫路线：预设输入→if当前角色状态=变量A+B+C+D+E→预设输出；if不是，则进入下一条if匹配
- （低级替代方案）简单路由路线：预设输入→简单路由
- 类比（**线性迷宫-穷举出口vs量子跃迁-虫洞穿梭**）

### 实现逻辑步骤（本人方案2）
1. 主模块收集当前所有相关变量的实值
2. 计算：当前路由ID = 变量A的值 + 变量B的值 + 变量C的值 + ...（字符串拼接）
3. 查询映射表：当前路由ID → 资源库ID
4. 输出：通过资源库ID获取对应的文本/表情/动作/语音
- 注释：其他方案也差不多的，就是进行了耦合程度变化，实现逻辑一致，就像你做同一数学题各种解题思路

### 映射表结构
- 路由ID（字符串） → 资源库ID（字符串）
- 变量A=1, 变量B=2 → 路由ID="12" → 资源库ID="RES_12"
- 注释1：变量的值不一定非要1234，任何符号都行，比如ABCD、喜怒哀乐等字符串、布尔值、数组、对象、null等等，只需要映射表对应ID（非字符串可以在映射表逻辑内部实现一个序列化层，将任何非字符串类型的值转换为字符串，用于生成路由ID）
- 我的建议是用<中文>进行值的填入，其次用<英文>，主要是看哪个比较短输入快，自由选择，<日语符号或者字母缩写>也行
- 映射表本质就是前ID到后ID的 符号→机器向量语执行逻辑→另一符号 的跳转而已，中文编程语法映射库适配也是这个思路，只不过是界面指令→机器向量语执行映射表逻辑（中转逻辑）→界面指令对应的机器向量语执行逻辑（落地逻辑）
- 注释2：香农已经给bit空信息填入0和1信息了，不需要重新定义，按他定义的底层逻辑写上层逻辑就行了
- 注释3：我就是直接搬运的航天领域技术别跟我说不行，传感器配置参数初始化→传感器读取非物理意义数据→按比例计算成物理意义数据→互补滤波或卡尔曼滤波融合数据→输出
- 注释4：只不过他们航天可能是一个数值按比例转换成另一个数值的映射，我是全域多变量状态唯一映射，就是promax通用版（输入-处理-输出整个流程哪个环节都可以用的虫洞穿梭-量子跃迁技术）
- 注释5：他们航天那么复杂的数据都能处理输出，我的多变量其实比他们环境简单一点，不涉及复杂数值计算，可行性完全不需要质疑的，而且航天的状态切换也是可以用我这个复合路由状态映射替代简单路由逐条守卫逻辑的，状态越多越复杂越是能体现效率优势性
- 注释6：多加废话一句，我就是觉得是航天复杂环境下可靠性极高的技术，才拿过来改良成我机娘高度拟人化行为输出的处理架构（真实感极强的深度互动虚拟角色你们想想有多么带感，文本/配音/表情/动作我可以无限拓展的，不可能一开始就是完美版，就是靠不停更新嘛）

## 复合路由状态映射拓展流程循环逻辑（对话系统特化，if代码的另一种方案）
- 前置说明：指数级增长≠无法使用，减少输入、变量、输出也可行，无需一步到位做到完美，强于旧范式即为提升，架构的上限是安全可控的深度拟人，下限是单一角色与角色间互动丰富性的拓展。
- 具体复合映射流程循环逻辑的广度深度可延展性:无数条映射中的一条映射如果要往下继续写的话，可以用二次分支输入-二次映射-递归-结束循环，就变成深度对话循环或自主机器人操作循环了。对于物理因果律，数学能精简成公式描述，逻辑代码也可以精简执行。
- **逻辑文字表达如下**：
- // 复合路由状态映射（精简代码行数）
- 输入：变量A+变量B+变量C
- 拼接：路由ID=A + B + C
- 查询：map[路由ID] → 资源库ID
- return 文本、形象、语音、场景 = 资源库ID
- // 映射后的后续可拓展流程循环（角色对话为例）
- 鼠标点击某一界面识别区触发
- 位置ID = 用户点击的界面位置
- 对应位置贴图文件命名为资源库ID
- 有贴图则提取ID，ID无贴图不触发反应，return默认无贴图
- 1资源库ID = 资源库ID + 位置ID → return除贴图选项的其他资源→点击→return贴图选项→点击
- 2资源库ID = 1资源库ID + 位置ID → …
- 递归：N资源库ID = (N-1)资源库ID + 位置ID，直到资源库ID无全部映射对象，return默认状态（脱离对话模式）
- if 所有识别区无贴图时，jump生效，点击画面任意一处自动推进对话
- 注1：美工做贴图，预设输入复用，减少代码冗杂度，增加一点贴图工作量，各个贴图只需要放不同文件夹，然后建立不同位置映射就行了，不看贴图含义，只看放置的位置，相当于把分支if return，改成了递归ID映射，功能没变，写法变了。用menu和if跳转节点守卫也是可以的，只不过我不想让代码行数太多，而且策划想改参数用映射表ID管理比较方便，不用改代码，改代码容易出BUG，能不动就不动。
- 注2：如果是物理机器人就需要电子屏幕做信号转接了，或者语音传感某个预留位置做积极中性消极意图识别但可能半天都触发不了不建议，95%识别率一律视为0%，不符合确定性指令需求，为了实时观测机器人各项状态，还是需要便携式电子屏幕的，想对话用户可以一边点一边说出来嘛假装在和机器人对话，日常轻度用概率也不是不行，真人有时也会听不清，但工业医疗等等就不适合了。

## 本架构技术方案的优势（概率性vs确定性）
- LLM模型，输入→大数据已有的大量同一物理规律的具象逻辑链拟合→计算拟合概率输出；只是穷举表面逻辑执行，不涉及深层逻辑状态映射。例如，花瓶是玻璃易碎材质，本身质量在跌落时施加引力加速度，重力势能转化为动能，与静止石地面接触后施加反作用力，于是花瓶跌落地面碎裂，这是一条逻辑链条，然后你再写人跌落地面变肉泥，高空抛物砸死路边野狗，其实就是简单路由+逐条守卫的数学算法（符号系统内自洽）
- 本人的元法则宇宙大模型，输入→复合路由状态映射（物理规律本身的状态映射，不依赖海量数据）→确定性输出；输入端→处理端深层逻辑状态映射→输出端执行结果输出。例如，你只需要让AI把跌落物视为一定质量的物体进行映射，跌落过程会受到重力势能，重力势能转化动能会损失能量，推动质量移动和抵消空气阻力消耗能量，剩下的才是动能，然后动能去撞击有质量的地面，会施加反作用力导致破裂，然后AI就懂这个状态了嘛，很简单的，就是我一直说的，识别→调用对应预设逻辑链→输出，根本不需要穷举的，其实就是复合路由状态映射的物理逻辑（可观测事实推演）
- Transformer架构AI的劣势（梦境复现现实）：云端连接需要联网、不可规避的幻觉输出、黑盒屎山难以维护、自我迭代会BUG堆叠、上下文或记忆库冗杂导致推理速度变慢、无法真正做到长期稳定人格互动、限制边界也有不可规避的穿甲风险、转嫁token成本给用户、新模型或增加模块无法解决底层架构的概率性输出致命点。
- 本人的CRSM-PARS新范式确定性架构调度AI的优势（现实创造梦境）：可不联网（不受电磁干扰）、无幻觉确定性输出（解决最后几毫米精度）、白盒可追溯维护（规避撇清法律责任的甩锅给AI行为）、不受上下文限制O(1)映射极速输出（精简字符与最优效率）、解耦式拓扑结构无限拓展（高附加值芯片更换）、可自主运行自我迭代（主逻辑次概率）、拟真机娘深度回应（复合状态人格进行稳定输出）、无需转嫁token成本给用户（确保广泛c端用户接纳度）、可用生成AI与人工筛选填充内容（驾驭生产力并落地应用）、可设置多次错误禁止访问来预防联网AI穷举法暴力破解篡改数据（物理结构外层算法防火墙）。
- **概率拟合生产力转为执行交付-检验成果-补全漏洞-更好地自主执行交付循环持续学习具象AGI终点**：比如说军事自主无人机让敌人逃脱了后反思整个过程的逻辑链条漏洞进行补全改进以便下一次完成任务目标，还能用历史数据算法计算启用哪条行动链的成功率高进行输出执行方案，就如同人的成长进化就是不停反思失败进行补全改进而来的，这个无人机一方面把失败原因发回给数据中心，一方面启用【反思改进】模块，开启算法概率计算空缺逻辑链节点中的最佳方案进行填入，再关闭【反思改进】模块重新回到【执行任务】模块（临时进化），数据中心研发工程师则对下一批机体进行迭代更新（长期进化）。

## 记忆系统的逻辑设计思路
- 当前生成AI的记忆插件问题：概率模型需要数据来改变权重进行猜测，什么应该遗忘，什么应该记住，缺少穷举的边界规则约束的话，混淆记忆是必然发生的事情。
- 玩家需要的记忆是什么：NPC记得之前和玩家一起做过的事、说过的话，会根据喜恶（记忆留存）改变对玩家的言行，NPC符合人设且要知道所在的世界观。
- 应该怎么设计：像矮人要塞、博登之门3会让玩家觉得这个世界是活的，不仅是依靠庞大的文本量，而且是设置了恰当的逻辑推进（蝴蝶效应），用预设的丰富来让玩家觉得是生成的涌现。反之，概率模型的生成往往是缺乏因果逻辑的，会让玩家觉得出戏。
